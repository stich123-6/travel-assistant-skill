# 四类业务流程

所有流程先遵循入口 Skill 的出发地、手机确认、真实回执约定。只加载当前需要的依赖，不做全量权限探针。

## 展会确认：先问名称，再搜索，查不到再问地址

该步骤用于用户已经决定参加某个展会、要求安排行程的情况，先于该展会相关的场馆搜索、路线和票务安排执行。外地与本市参展都适用。

1. **先确定展会名称。** 从用户本次输入、已确认的上下文或用户提供的邀请函/链接中提取名称；只有“农业展会”“行业展”“上海的一个展会”等类别或城市描述不算具体名称。没有名称时先问：“你要参加的展会叫什么名字？”已有城市和日期保留，不重复询问，此时等待回复，不先查近期同类展会或推荐一个场馆。用户提供的简称足以指向具体展会时可按简称搜索，不强求官方全称。
2. **取得名称后，针对该名称搜索。** 使用宿主实际可用的联网搜索/网页读取能力，把已知城市、参加日期及必要的届次作为条件；优先核对主办方、展会官网或会场发布的该次活动信息。只围绕用户指定的展会检索，不长时间罗列全市近期展会。没有搜索工具时说明当前无法联网核实，再进入地址补问，不把未执行搜索说成无结果。
3. **搜索能确认本次活动及场馆时，使用有来源的结果。** 只搜到同名往届、外地场次、已经结束的活动，或来源与用户日期/城市冲突，均不算确认了本次活动。多个同名场次让用户选择；日期冲突只说明查到的来源与本次安排不一致，询问该场次或地址，不能认定用户说错，更不能换成另一个农业展会。
4. **搜索没有查到，或仍不能确认时，再问地址。** 简短说明：“还没查到能确认这场展会的信息，请提供展会的具体地址或定位，我再安排路线。”可接受详细地址、地图定位、明确的场馆及入口、邀请函或活动链接。用户已经提供清楚地址时直接复用，不重复问。
5. **地址明确后再进入规划。** 用腾讯地图解析用户确认或有可靠来源的地址；有多个地点候选再请用户选。地图只能确认地点，不能单独证明某展会在该处举办。按用户提供地址规划时注明地址来源，不额外编造展会名称、主办方、举行时间、门票或活动是否存在；缺少到场时间再按后续阶段补问。

用户明确说“不知道展会名称，就按这个地址规划”，且已给出可定位的地址时，可以按其明确要求进入路线规划，不反复卡住名称，也不声称已确认展会信息。用户本来就要求“帮我找/推荐上海明天有哪些农业展会”时属于活动发现，可以按类别搜索真实候选；用户选定后再规划，不能混同于已经要去某场活动的行程请求。

**截图场景的首轮示例：**

用户：“我明天下午需要去上海参加一个农业展会，帮我规划一下行程。”

助手：“你要参加的展会叫什么名字？”

取得名称后再搜索。不要在首轮用某个常见农业展馆、过期展会或同日其他类型活动来代替用户的目的地。

## 外地出行 / 外地参展参会

1. 提取出行目的、出发城市、目的城市、活动日期、活动时间、场馆和已知交通偏好。参展先完成上面的展会确认步骤。普通出游没有会议开始时间时，不强求参会字段；以用户的出行日期、天数或已明确活动约束规划。
2. 展会确认后，需要规划本次门到门路线而出发地不明确时，再问家、公司或其他位置；选中别名但没有地址，再问具体地址。单独的城际查票请求只要出发城市等参数已知即可先查票，但不能为未明确的展会猜地点或擅自确定到达站。
3. 用户提供的邀请函、场馆链接可作线索；对缺失字段用补信息卡。展会名称不能唯一确定日期或城市时，不把另一个城市或往届活动作为本次活动。
4. 用腾讯地图确认场馆位置、入口和两端接驳路线。城市不明确或有多个候选，交给用户选择。
5. 需要车票或机票时调用同程：明确高铁/火车用火车查询，明确飞机用机票查询，未指定方式而希望比较交通用综合交通查询。把最晚到场、接驳缓冲、人数及价格偏好完整传入。以实际返回为准。
6. 先检验能否按时到达，再比较全程耗时、价格、换乘和出发时间。明显赶不上活动的结果不要标为可行方案；需要前一天到达时说明理由，住宿按需处理。返程未确定不阻塞去程，不编造返程日期。
7. 行程包含：出发地到站/机场、城际交通、到达站/机场到会场、活动、用户已明确的返程。票务未预订标为“候选/待购票”；只有实际票据或订单支持时才标为已预订。
8. 打车仅查价、生成跳转入口还是实际叫车，按用户意图区分。用户只批准行程或日程时，不下单。
9. 生成场景准备清单，展示精确到日期和时间的确认卡；经同意写手机系统日历。默认提议主活动日程；交通日程只有在卡片列出且用户同意时才单独创建。

**时间计算**：本市直达活动建议出发时间 = 最晚到场时间 − 地图预计路程耗时 − 到场及路况缓冲。到站/机场的时间另考虑车次/航班办理、安检、步行等缓冲；标明缓冲是建议值，不冒充承运方要求。多段行程从确定的车次/航班时刻逐段倒推，不把所有路段简单相加后忽略时刻表。

远期出发时间只能使用当前可用的路线估算。天气或路况没有覆盖出行日期时说明查询范围，不冒充远期预测。需要出发前复查时，只有实际创建了对应任务才承诺会复查。

## 本市会议 / 展会 / 拜访

1. 提取具体日期、开始时间、最晚到场要求和场馆。参展先完成上面的展会确认步骤，再补问本次出发地等必要信息；普通会议、拜访按已有信息处理，不强制索要展会名称。不因本市活动自动选公司。
2. 腾讯地图解析出发地与会场。不同园区、馆号、入口影响路线时补齐必要定位；不要过早索要与路线无关的展位细节。
3. 按用户选择查询驾车、公共交通、步行或骑行；没有偏好时按实际距离和可达性给出少量合理方案。地图只返回驾车耗时时，不自行声称等于打车总耗时或包含等车时间。
4. 计算建议出发与到场时间，补充签到/访客登记、携带材料等准备事项。需要查价或叫车再转滴滴。
5. 展示活动、路线、准备事项和拟写入手机系统日历的范围；结束时间未知仅在这一阶段补问。

## 备忘录 / 提醒本人

先区分三个含义：

| 表达 | 操作 |
| --- | --- |
| “记一下……”，未要求提醒 | 仅记录事项；不强制问提醒时间 |
| “周五交方案，周四9点提醒我” | 截止时间和提醒时间分开；提醒对象是用户本人 |
| “每天9点提醒我……” | 明确重复规则、时区和必要的起止范围 |

提醒时间含糊时只补问缺项；“提前一天”但没有时刻时提议具体时刻，取得同意。未指定提醒渠道时，在确认卡展示拟用手机系统日历及其提醒能力，让用户选择或同意。

优先使用已接入且能设置通知的系统日历能力创建事件/提醒；只有截止时间的待办不等于闹钟。纯提醒需要映射为日历事件时，展示这一形式及必要持续时间供用户同意，不擅自把它变成会议。

提醒完成依据：提供方确实接受提醒设置，或真正的调度工具成功返回任务标识。只有记录、日程备注或 `.ics` 文件时，状态仍不是提醒已设置。系统日历未接入且无调度时，保存待执行提醒并明确缺口。

## 钉钉立即 / 定时通知

1. 分清“提醒我联系某人”与“发消息给某人”。只有后者执行对外发送。
2. 使用钉钉已安装 Skill 的联系人搜索；唯一匹配才可继续。同名时展示必要的部门等辨识信息，禁止默认发给第一个人或所有同名者。
3. 提取消息正文和发送时间。用户已给出明确正文、唯一收件人并要求立即发送，已有指令就是本次发送授权；若正文由助手起草或发送时间含糊，展示对应卡片补齐或确认。
4. 用真实收件人ID和正文执行，保存实际返回的消息标识/回执。返回错误时显示未发送；结果未知时先查回执，不盲重发。
5. 定时发送需要已接入的可持久调度工具。创建任务时固化唯一收件人ID、消息全文、时间、时区、授权范围和记录版本；任务到点时不依赖旧对话猜测这些数据。
6. 创建定时任务前确认运行环境到点能执行、持有有效钉钉授权，并支持所需发送操作。未接入时保留“待调度”，不得提前发送、以睡眠等待代替任务，或把本人的日历提醒冒充向他人发出的定时消息。
7. 仅按用户明确需要使用 DING，不把普通消息升级为紧急通知。

## 混合意图、修改与取消

- 一个主行程可关联交通、准备提醒、消息等多个子任务。共享用户已经确认的日期、地点，外部写入授权分别记录。
- 输出“行程已规划；消息已发送；日程待接入；准备提醒未设置”等逐项真实结果。
- 修改方案先更新版本，再重新计算受影响的路线、缓冲、日程及尚未触发的提醒/定时消息；已发送的消息不能当作可自动撤销。
- 根据用户此次明确的修改/取消范围执行；不要顺带取消车票或打车订单。取消日程不自动推断为取消所有关联订单。
- 已写日程按提供方与ID更新，不以新建替代修改。日历未接入时只更新待创建数据。旧卡片失效；有变化的写入范围展示给用户核对。
