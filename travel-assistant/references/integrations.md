# 依赖与接入规则

腾讯地图、同程和滴滴按[MCP运行约定](mcp-connectors.md)调用。此Skill只编排宿主实际提供的能力，不保存凭证，不自行启动供应商CLI或脚本。钉钉保持原接入范围；系统日历保持待接入。

| 角色 | 接入方式 | 本助手使用范围 |
| --- | --- | --- |
| 地图 | 腾讯地图官方MCP，地址已核实；目标云端授权未验证 | 地点搜索、路线规划、距离耗时、适用日期的天气 |
| 票务 | 同程MCP；当前官方地址与schema待确认 | 机票、火车票、适用的综合交通查询 |
| 打车 | 滴滴官方MCP，地址已核实；目标云端授权未验证 | 预估车费、手机跳转入口、用户明确要求的叫车与查单 |
| 钉钉 | `dingtalk-unified` | 联系人解析、立即消息；已接入调度时的定时消息发送 |
| 手机系统日历 | 尚未接入 | 保留目标与待创建日程，后续绑定实际 Skill／连接器／移动端桥接 |
| 定时调度 | 运行时按需发现 | 创建真实可持久任务，不能以本地记录替代 |

每次新任务按宿主当前连接器列表、启用状态和真实工具schema发现能力，按需验证授权；不因旧任务成功或Skill已安装就宣称云端可用。用户只要求规划或记录时，不先连接所有服务。

## 腾讯地图

读取[腾讯地图MCP约定](tencentmap-mcp.md)。定位使用实际提供的`geocoder`、`placeSuggestion`等工具，路线使用`directionDriving`、`directionTransit`、`directionWalking`、`directionBicycling`等；参数以当前schema为准，不能沿用旧Python方法签名。

取真实返回的坐标、POI ID、距离、耗时和查询时间。主路线始终由腾讯地图处理；地图未接通时说明该步骤待接入，不擅自换成滴滴或其他地图。滴滴订单自身需要的地点解析仍属于滴滴流程。

## 同程程心

只使用当前宿主提供且已确认来源的同程MCP工具，按真实schema选择机票或火车票能力，传入出发地、目的地、日期、到达限制和用户其他约束，不编造工具名或把原来的`flight-query.js`、`train-query.js`当成MCP工具。

目前未核实同程官方MCP端点和schema；原`tc-chengxin`为脚本/CLI接入，不能仅凭“连接器”名称就认定它是MCP。本版不自动切回同程CLI取Token。没有真实MCP时标记查票待接入，保存非秘密查询条件。

保留实际返回的票价、余票、排序、日期、站点/航班和手机预订入口，不编造资源。若真实MCP返回可直接展示的`markdown`或声明输出契约，保留原始表格、预订列、手机链接、二维码和客服信息；无对应字段时按实际结构展示，不假设存在旧脚本的JSON边界或本地HTML产物。

查询返回的预订入口不等于订单；用户点开入口购票后，只有票据、订单回执或用户明确确认的信息才能用于已购票日程。

## 滴滴打车

先读[滴滴 MCP 接入](didi-mcp.md)，只使用当前宿主已连接的滴滴官方远程MCP。工具存在且调用成功时，不因缺少本地 `didi-ride-skill`、OpenClaw 或 mcporter 而报未接入；MCP不可用时保持待接入，不自动降级到CLI。参数以宿主公开的真实schema为准。

- 地点先通过滴滴要求的`maps_textsearch`解析，用户本次选择的家/公司必须展开为已确认的具体地址。多候选依其规则交用户选；不得因读到历史偏好就替用户选择出发地。
- 查价使用`taxi_estimate`，保存真实`traceId`和实际可用车型。只问价格不创建订单。
- 用户希望手机打开滴滴完成叫车时，若当前版本提供`taxi_generate_ride_app_link`，使用真实上下车点生成入口；点击入口不等于已叫到车。
- 直接叫车需先展示本次预估的车型和价格，取得对应的明确下单同意；已有同一范围的同意不重复询问。`taxi_create_order`使用当前有效预估得到的`estimate_trace_id`和`product_category`，手机号按其契约可选；不要把预估坐标字段误传给下单接口。
- 不把“建议打车”“同意行程”“同意创建日程”当成叫车指令。预约叫车和自动查单需要宿主实际可用的调度能力，不假定存在OpenClaw cron；缺少调度时不得声称已预约或已安排自动回查。
- 下单超时或返回结果不明时先核实订单；明确要求停止重试的错误遵循其处理规则，不盲目再次下单。

## 钉钉消息与联系人

读取`dingtalk-unified`的`SKILL.md`及其`references/products/contact.md`、`chat.md`相关部分。命令可随版本变化，以`dws ... --help`或`dws schema`为准，写操作只使用已获授权范围。

当前说明中的相关命令：

- `dws contact user search`：通过关键词获得候选，再确定唯一用户ID。
- `dws chat message send`：以当前用户身份给唯一用户或群发送正文。
- `dws chat message send-by-bot`：仅当用户选择且授权允许的机器人发送场景适用，不作为单聊权限不足时的自动绕过。

同一发送动作只选择一个目标类型，不能把姓名当用户ID。支持`--dry-run`时先准备并核对；已展示且已获明确同意的摘要无需重复让用户确认。具体返回字段按真实schema解析并保存消息回执，发送失败不能显示已发送。

钉钉套件虽然包含`calendar`和`todo`，本项目目标是手机系统日历，**不能擅自改为调用钉钉日历**。`todo`的截止时间也不能被当作手机定时通知已设置。

## 手机系统日历：待接入边界

用户已明确选择：暂不接入，先生成本包。配置模板中`provider`和`calendar_id`为空，状态为`not_connected`；没有假定的API或占位可执行命令。

后续用户要求接入时，从宿主实际已有的日历Skill、连接器或移动端桥接中确定一种可用入口。若没有，说明需要新增接入，不静默安装或索要账号密码。

接入时需要确认：

1. **目标归属**：手机系统日历实际使用的账户、目标日历名称及ID。若通过云账户写入，确认手机系统日历已配置该账户和同步；云端写入与设备可见分别报告。
2. **实际能力**：是否能查询、创建、更新、删除、设置提醒，是否支持全天、时区、重复、幂等或客户端关联标识。只使用真实schema支持的字段。
3. **授权与执行环境**：当前执行位置能否访问已授权账户/设备；手机点击同意能否由宿主执行该接口；系统通知权限不由API写入成功推定。
4. **回执**：创建的event ID或等价标识、目标日历、时间和提醒配置。能读回时核对；写入回执不含提醒信息且无法读回时，提醒标记未验证，不冒充完成。

准备写入的数据应包含标题、开始结束或全天日期、时区、真实地点、路线摘要、准备清单、已同意提醒及本地关联ID。默认创建个人日程；没有邀请指令时不添加参会人，以免触发邀请通知。

这是一份数据与行为约定，不是某个日历产品的调用接口。字段映射必须在选定真实工具后完成。保留provider、calendar ID、event ID用于更新和取消。手机没有同步证据时输出“已写入指定日历，手机同步状态尚未确认”。

能力缺失时继续提供方案和待创建数据。只有用户另行选择时才提供`.ics`导入文件；必须说明需要导入，导出不计作自动创建。快捷指令链接、安卓插入界面等只有真实执行并返回成功才可标为创建，否则只是待用户完成入口。

## 提醒与定时消息

优先使用系统日历真实支持的提醒设置。日历不支持所需提醒时，只在用户同意的其他已接入调度渠道执行，不偷偷替换。

WorkBuddy或其他宿主若提供定时工具，先读当前工具schema，确认一次性/重复规则、时区、执行位置、到期运行条件、结果查询与取消方式。不要把Codex的工具名称、自动化标记或手写cron规则当成WorkBuddy必有接口。

用户同意提醒或定时发消息后，创建包含完整上下文的持久任务并保存实际任务ID。任务执行前重新核对版本与是否取消；只执行已经同意的操作。没有真实调度入口或有效授权时标记`waiting_scheduler`，说明没有安排到点执行。不能保证机器离线仍执行的任务，应在确认卡说明运行条件。
