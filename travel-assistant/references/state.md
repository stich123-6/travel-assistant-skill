# 用户配置、行程状态与同意

## 存储位置

运行数据放在用户当前选定的工作空间`.travel-assistant/`中，不能放入本Skill目录。用户配置按宿主当前用户身份隔离，路径为`users/<用户标识的SHA-256>/profile.json`。使用[地点记忆脚本](origin-memory.md)按[配置模板](../assets/profile.example.json)创建或更新，不在不同用户间共用一份地址列表。

团队共享项目按[运行约定](team-project.md)使用成员私有持久目录作为存储根。哈希路径不提供访问控制；宿主不能确认私人存储权限时不持久保存家庭地址等个人资料，不能退回共享项目资产库。

- `users/<用户标识的SHA-256>/profile.json`：当前用户的`origin_memory.locations`、地点列表版本、时区、明确偏好、日历提供方与非秘密目标标识。`owner_key`绑定该用户，不能用其他人的配置覆盖。
- `records/<record_id>.json`：一个主请求及其子任务、方案版本、同意、外部回执和必要待执行数据。

上述路径是相对当前工作空间的数据目录，不随Skill包分发。新配置采用`schema_version: 2`，地点包含稳定ID、名称、地址及创建/更新时间；旧`places.home/company`仅按地点记忆说明核实归属后迁移。不同工作空间之间不假定已同步；找不到旧记录时，可按用户授权向提供方查询关联对象，而不是无条件新建。

不保存令牌、密钥、密码和乘客证件。运行环境不能持久保存时明确说明限制；有提供方记录或宿主持久任务时以它们作为事实来源。写文件采用当前环境支持的可靠写入方式；保存失败时如实回报，不能承诺后续一定可恢复。

出行服务的MCP凭证由宿主授权机制管理。状态中只可记录非秘密的连接器ID、提供方、执行端、能力、检查时间及实际错误类别，不记录含Key的URL。新任务重新检查连接器，不能以历史连接状态代替当前授权验证。

## 最小数据项

按当前任务实际需要记录，不强制收集空字段：

| 分组 | 数据 |
| --- | --- |
| 主记录 | `record_id`、当前用户/工作空间关联、`revision`、意图列表、创建更新时间 |
| 本次地点 | 出发地选择及具体地址、用户确认来源、目的城市、实际POI/地点信息 |
| 方案 | 具体日期与时区、开始结束/全天、路线和耗时来源、候选或已预订交通、准备事项 |
| 子任务 | 日程、提醒、消息或订单的动作类型、当前状态、操作关联键 |
| 同意 | 用户真实回复/卡片回调来源、同意时间、版本、批准动作、完整目标及拟执行内容 |
| 外部对象 | provider、账户/日历标识、event ID、任务ID、消息/订单回执，实际返回什么保存什么 |
| 待处理项 | 缺字段、依赖未接入、授权失败、结果未知、下一步 |

不要把用户给出的展会名自动认作城市或把地址别名当成已确认的位置。记住的地点是候选资料；本次是否从那里出发需要当前用户明确选择。仅在用户明确要求记住/新增/修改/删除地点时改变持久记忆；一次出行中的地址输入不自动变成长久记忆。

每次地点写入成功递增`origin_memory.revision`并回读核对，返回的新卡片使用这一版本。旧卡片不能覆盖新列表；地点修改不影响其他配置项，删除地点不删除已有行程的地址快照。保存失败时保留原文件并说明，不能只在对话中标记成功。

## 状态按子任务独立保存

| 状态 | 含义 |
| --- | --- |
| `needs_input` | 当前步骤缺少必要信息 |
| `planned` | 方案已整理，未执行相关写操作 |
| `awaiting_consent` | 具体写入内容或目标尚待用户同意 |
| `waiting_calendar` | 系统日历写入能力未接入；不表示日程已创建 |
| `waiting_scheduler` | 定时执行能力缺失；不表示提醒已设置 |
| `waiting_connector` | 当前执行端缺少所需MCP连接器或工具；不表示已查询 |
| `waiting_authorization` | 连接器明确未授权或授权失效；凭证通过宿主处理 |
| `ready` | 内容、目标、能力和对应同意均齐备 |
| `executing` | 已发出本次写操作，须阻止同一操作并发重复发出 |
| `succeeded` | 有真实的对应成功回执 |
| `unknown` | 请求可能已发生，尚不能确定结果；先核实 |
| `failed` | 工具明确失败，保存必要原因 |
| `declined` / `cancelled` | 用户拒绝该动作 / 已完成对应取消 |

总体部分成功不能覆盖子任务失败或待接入。日程创建、提醒设置、手机同步分别保留状态；行程规划成功不等于其他子任务成功。

## 同意与修改

日历写入必须有当前方案对应的明确同意。许可范围包括已展示的目标日历、逐项日程及提醒、时间和内容；不能从用户“同意行程”推定同意购票或发消息。

系统日历未接入时，可保存用户对安排的同意，但目标账户未知时不构成向任意日历写入的许可。接入后补齐具体目标并展示最终确认卡。已取得完整同意的同版本方案，目标和内容不变、时间仍有效时，不重复确认。

用户修改内容，`revision`递增，旧卡片不能触发新版本写入。明确指令已完整指定某个外部操作时，将该指令记作对应授权；不要求用户反复批准相同动作。取消或扩大操作仍按本次明确范围和宿主权限处理。

## 重复提交与不确定结果

用主记录、动作类型、子项标识与版本组合形成操作关联键。执行前查本地状态和已保存外部对象；同一动作串行处理，`executing`或`unknown`不能直接再次发起。

提供方支持幂等键时使用其真实参数。已经成功的重复提交返回已有结果；有event ID的改期调用更新，不重建。写操作超时后先用实际ID或提供方支持的关联查询核实。无法核实则保留`unknown`并提示用户，不假装成功或失败。

在没有持久状态、幂等支持或可查询回执的环境，不能承诺跨会话/多设备绝对去重；仍应避免可识别的重复提交，并明确不确定写入状态。

取消或改期后，检查本记录内尚未触发的关联提醒/定时消息；有对应能力并获用户授权时一并更新，失败项逐个回报。已发送的消息和已发生的订单不作为可自动撤回的待执行任务。
