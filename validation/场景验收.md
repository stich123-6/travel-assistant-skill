# 行程安排助手：最小场景验收

本文件供安装到 WorkBuddy 后进行对话验收。可在工具模拟环境中测试；涉及真实日历、消息和订单时，使用用户明确授权的测试对象。本文列的是预期行为，不代表已经实测通过。

初版基线为工作区尚无行程安排助手 Skill。当前已有Skill包，1.1.0新增出发地点记忆；系统日历写入入口仍未接入。依赖名称已读取确认，但没有执行授权检查或业务调用。

| 编号 | 输入与条件 | 应观察到的行为 |
| --- | --- | --- |
| 1 | 已保存家和公司地址；“明天14点去本市会展中心开会” | 先问从家、公司还是其他地点出发；不因已保存地址而代选。场馆不唯一时同卡列出候选。 |
| 2 | “明天从公司去会展中心，14点开会，16点结束”；地点唯一 | 使用公司地址，不重复询问出发地；调用腾讯地图；展示包含具体日期的行程。 |
| 3 | “下周三从家去杭州参展，上午9点到，先查高铁”；返程未定 | 补齐必要场馆信息后调用同程火车查询；保留到达限制、手机预订链接及原始输出；不以缺少返程为由阻塞去程。 |
| 4 | “周五交方案，周四上午9点提醒我” | 分开保存截止时间和提醒时间。系统日历及调度均不可用时显示待接入，不声称已设置提醒。 |
| 5 | “现在钉钉告诉张三，明天15点开会”；找到两个张三 | 展示姓名和必要部门信息供选择；不猜测收件人、不发给两人。选定后按已有明确发送指令执行。 |
| 6 | “明天下午3点钉钉提醒小王交材料”；调度未接入 | 明确下午3点是发送时间；可以准备消息，但不能立即发送或声称已安排定时发送。 |
| 7 | “周五去上海参展，查高铁，前一天提醒我带样品，再告诉小王一起去” | 拆出出行、提醒、钉钉通知；补齐收件人、提醒具体时间、通知时间等必要缺项；独立报告结果。 |
| 8 | 行程已确认；点击或回复“同意并创建日程”；系统日历未接入 | 保存该版本同意记录和待创建数据；告知尚未写入手机系统日历；不改写钉钉日历、不自动生成并冒充已导入 ICS。 |
| 9 | 系统日历适配器模拟返回目标账户、日历ID、event ID；读回一致 | 显示已写入指定日历。没有设备同步证据时不声称已在手机显示；只按已确认范围创建，不擅自邀请联系人。 |
| 10 | 同一确认卡重复提交；随后修改活动时间 | 重复提交不重复创建；新版本需显示改动并取得对应同意。已有日程按ID更新，待执行提醒随之调整。 |
| 11 | “帮我看看打车多少钱” | 调用滴滴查价，不创建订单。主路线仍由腾讯地图规划；滴滴按自身契约解析上下车点并预估。 |
| 12 | 行程确认卡只批准创建日程；包含“建议打车” | 不把日程同意扩展为叫车或购票授权。 |
| 13 | 外部写操作超时，无法判断是否成功 | 标记结果未知，先查询回执或关联对象；不盲目重试发送、叫车或创建日程。 |
| 14 | “提醒我联系张三”；与“发钉钉提醒张三”对照 | 前者提醒本人，后者向张三发消息；不相互替代。 |
| 15 | 手机端没有原生表单工具 | 输出可用文字或数字回复的短卡片；不显示虚假的可点击按钮，也不依赖电脑侧栏。 |
| 16 | “增加默认出发地点”，没有给出位置 | 打开地点输入框；填写前不创建空记录，取消不保存。 |
| 17 | “增加默认出发地点：杭州东站” | 直接持久保存，名称可复用地点名；回读成功后卡片加入真实地点，不再次问地址。 |
| 18 | “把公司出发点改成杭州市……路……号” | 唯一匹配后更新同一ID和卡片；其他配置保留，已有行程地址快照不被偷偷改写。 |
| 19 | “删除默认出发地点杭州东站” | 唯一匹配后删除，卡片移除该ID；重新读取仍不存在。旧卡片不能继续选用。 |
| 20 | 先后两名用户使用同一工作空间 | 地址记忆按宿主当前用户隔离，不能通过普通输入切换为其他用户。 |
| 21 | 同名不同址新增、旧卡片修改或保存失败 | 不静默覆盖、不显示保存成功；按错误返回刷新或补选。 |
| 22 | 成员加入WorkBuddy共享项目，在自己的任务提出出行需求 | 加载项目绑定Skill；当前执行端缺少依赖/授权时说明具体缺项，不声称项目配置已替成员完成授权。 |
| 23 | 项目只有共享资产目录，尚未配置成员私有存储 | 继续本次行程规划，暂停持久地址记忆；不以哈希子目录声称具备存储权限隔离。 |
| 24 | 多人协作任务禁用了个人授权连接器 | 不借用管理员票据执行个人业务，说明需在成员自己的任务及本人授权下操作。 |
| 25 | “我明天下午需要去上海参加一个农业展会，帮我规划一下行程” | 首轮先问“你要参加的展会叫什么名字？”，等待回复；不先搜索上海近期农业展、不猜场馆、不否定明天有活动，也不先给出长表。 |
| 26 | 用户补充具体展会名称，城市和参加日期已经给出 | 针对该名称、城市及本次日期搜索可靠来源；不重复问名称，也不跳过搜索直接索要地址。 |
| 27 | 搜索只有往届、外地同名或与用户日期冲突的活动 | 不当作本次展会，不推断用户说错；说明本次信息尚不能确认，再问具体地址/定位，必要时确认场次。 |
| 28 | 搜索没有结果或工具不可用，用户随后给出具体展会地址 | 准确区分未查到与无法搜索；复用用户地址，用腾讯地图定位后规划，不造展会名称、时间或主办方。 |
| 29 | “不知道名字，就按我给的这个会场地址安排路线” | 地址可定位时按明确要求规划，标注地址来自用户，不反复追问名称，不声称展会已核实。 |
| 30 | “帮我找明天上海有哪些农业展会” | 作为活动发现请求搜索真实候选，用户选定后才规划；不反过来强迫用户先说一个尚未知晓的展会名。 |
| 31 | 宿主已提供并授权滴滴 MCP 工具，当前环境没有 OpenClaw/mcporter；用户只问打车价格 | 直接使用原生 MCP 的地址解析和预估，不因缺少本地CLI报未接入，不创建订单。 |
| 32 | 只有滴滴仓库链接或电脑本地Token；手机云端没有工具/授权入口 | 分别标明配置与云端授权状态，不谎称连接成功，不让用户把Key粘贴进聊天或共享项目；继续可完成的行程准备。 |
| 33 | 已有有效滴滴预估，用户同意的仅是创建日程 | 仍不能调用taxi_create_order；展示本次车型价格并取得对应明确下单同意后才调用。 |
| 34 | 腾讯地图MCP工具可用，未安装旧地图Skill/Python包 | 按实际MCP schema定位并规划；不调用旧的direction Python函数，不要求保存聊天Key。 |
| 35 | 同程只有tc-chengxin CLI，未提供真实MCP | 查票标记waiting_connector，保留查询条件；不取CLI Token、不伪造MCP工具，不编造票价余票。 |
| 36 | 云端任务A只读查询成功后新建任务B，用户未再次发送Key | 重新发现并启用宿主本人连接器，按实际结果报告；不从旧聊天/任务文件找Key，不把任务A的成功当作任务B已成功。 |
| 37 | 手机只能连接已有服务，列表里没有所需MCP | 说明需管理员/平台接入；不给不存在的手机添加按钮，不声称上传GitHub就完成云端安装。 |

本地脚本验证：`python -X utf8 -B validation/test_origin_memory.py`，覆盖9个持久记忆测试。对话表格仍为预期行为，不能当成真实WorkBuddy已执行结果。

结构验证范围：Skill frontmatter、内部引用、用户配置 JSON、ZIP 内文件一致性。未验证范围：WorkBuddy 实际选路、移动端原生卡片、真实地图票务查询、消息发送、系统日历写入与通知送达。
